# Founder Support Tracker

A small web app for routing entrepreneur support requests to regional partner organizations.
I built it as the EnterpriseKC technical interview project, with a one-hour budget.

**Live URL:** https://ekc-support-tracker.vercel.app (API docs at /api/docs)  
**Source:** https://github.com/jdhillen/ekc-support-tracker

## The problem

Founders often need help (capital, legal, hiring, mentorship), and that help is spread across many
separate organizations. Requests arrive by email or word of mouth, nobody can see where one stands,
and handoffs between organizations get lost. This app gives one place to:

- **Log** a founder's request (who, what business, what kind of help, how urgent)
- **Route** it to a partner organization
- **Track** it through `New → Referred → In progress → Resolved`
- **See** the overall pipeline at a glance (counts by status, search, and filters)

## Architecture

```
Browser (Vue 3 SPA)
   │  fetch /api/*  (same origin)
   ▼
Vercel ── static files (Vite build: dist/)
   └──── /api/* → api/index.py (FastAPI, Python serverless function)
                     │  psycopg, one connection per request
                     ▼
               Supabase Postgres (transaction pooler, port 6543)
```

Everything runs as one Vercel project and one deploy. The front end and the API share an origin, so
CORS isn't needed.

### Front end (`src/`)

| File | Role |
|---|---|
| `App.vue` | Page state: the list, filters, partners, and which request is open in the dialog. Calls the API. |
| `components/StatsBar.vue` | Count by status; clicking a count filters the list. |
| `components/RequestTable.vue` | List view with an inline status dropdown for fast triage. |
| `components/RequestForm.vue` | Create/edit dialog (native `<dialog>`). Shows API validation errors. |
| `api.js` | Thin `fetch` wrapper. Turns FastAPI error payloads into readable messages. |
| `constants.js` | Statuses, categories, and priorities (these mirror the backend). |

### Service layer (`api/`)

| File | Role |
|---|---|
| `index.py` | FastAPI routes: HTTP concerns only (status codes, 404s, 400s). |
| `_schemas.py` | Pydantic models. Every input is validated before it reaches SQL. |
| `_repository.py` | All SQL. Parameterized queries; `psycopg.sql` builds dynamic `UPDATE`s. |
| `_db.py` | A per-request connection as a FastAPI dependency. Commits on success, rolls back on error. |

Files in `api/` that start with `_` are helpers, so Vercel doesn't deploy them as their own functions.

### API

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/requests?status=&q=` | List requests, with optional status filter and text search |
| GET | `/api/requests/{id}` | Get one request |
| POST | `/api/requests` | Create a request |
| PATCH | `/api/requests/{id}` | Partial update (status, partner, details) |
| DELETE | `/api/requests/{id}` | Delete a request |
| GET | `/api/partners` | Partner organizations (lookup table) |
| GET | `/api/stats` | Counts by status |
| GET | `/api/health` | Liveness check plus a DB check |
| GET | `/api/docs` | Interactive OpenAPI docs (generated by FastAPI) |

### Data model (`db/schema.sql`)

- `partners`: id, name, focus
- `requests`: id, title, description, requester name and email, business_name, category, priority,
  status, partner_id → partners, created_at, updated_at

Allowed values are enforced in three places: `CHECK` constraints in the database, Pydantic `Literal`
types in the API, and dropdowns in the UI. Row-level security is turned on with no policies, so
Supabase's public REST API can't read the tables. The app connects as the table owner instead.

## Running locally

```bash
cp .env.example .env              # paste your Supabase transaction-pooler URL
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
npm install

npm run dev:api                   # FastAPI on :8000 (docs at /api/docs)
npm run dev                       # Vite on :5173, which proxies /api to :8000
```

## Deploying

1. **Supabase:** create a project. In the SQL editor, run `db/schema.sql`, then `db/seed.sql`.
   Copy the **Transaction pooler** connection string from **Connect**.
2. **GitHub:** push this repo.
3. **Vercel:** import the repo (or connect it under Project → Settings → Git) (the Vite preset is detected automatically). Add the environment
   variable `DATABASE_URL`, then deploy. Vercel builds the Vue app and deploys `api/index.py` as a
   Python function.
4. Check `https://<app>.vercel.app/api/health`, which should return `{"status":"ok"}`.

## Decisions made for the one-hour limit

- **One platform, one deploy.** Vercel hosts both the static front end and the Python API. That
  means no CORS, no second host, and no cold starts from a free tier that sleeps.
- **Managed Postgres instead of SQLite.** Serverless functions have no persistent disk. Supabase's
  free tier gives a real relational database with constraints.
- **No ORM and no migration tool.** A few hand-written, parameterized SQL queries in one repository
  module, plus one schema file. Easy to read and explain.
- **One connection per request through the transaction pooler.** That's the right pattern for
  serverless. A connection pool inside a short-lived function would mostly sit unused.
- **No authentication.** It's a demo; in production this is the first thing to add.
- **Partners are seeded and read-only.** There's no admin screen to manage them.
- **No pagination, and any status can move to any other status.** Fine for demo-sized data.
- **Plain CSS, no component library or router.** One screen and one dialog cover the workflow.
- **Allowed values are listed in both the UI and the API.** They could be served from an endpoint.

## With more time

1. **Auth and roles.** Supabase Auth with separate views for founders (submit requests, track their
   own) and partner organizations (see only what's referred to them).
2. **Activity history and comments.** A `request_events` table that records every status change and
   note, as an audit trail for each handoff.
3. **Outcome metrics.** Time to referral, time to resolution, and load per partner. Turns the
   tracker into evidence of impact.
4. **Notifications.** Email the partner when a request is referred to them, and email the founder
   when the status changes.
5. **Workflow rules.** Valid status transitions, with "Referred" requiring a partner.
6. **Scale and quality.** Pagination, full-text search, Alembic migrations, pytest plus Vitest, CI
   on pull requests, error tracking (e.g. Sentry), and rate limiting on the public form.
7. **Partner directory.** A CRUD screen for partners, plus matching on category and focus to
   suggest the right partner automatically.
